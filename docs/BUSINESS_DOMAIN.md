# GeoKZ — бизнес-логика и предметная модель

## 1. Главная задача

GeoKZ должен быть единым рабочим окном по геологической информации Казахстана.

Пользователь выбирает территорию, месторождение, геологический объект или скважину и получает максимально полную доступную информацию из:

- встроенной проверенной базы GeoKZ;
- официальных открытых источников Казахстана;
- международных открытых геологических источников;
- загруженных пользователем документов и файлов;
- GIS/геофизических наборов;
- результатов бурения, каротажа, испытаний и интерпретаций;
- исторических отчётов и публикаций.

Каждое значение должно иметь происхождение: источник, документ/файл, дату получения, метод извлечения, статус проверки и, где возможно, точную страницу/интервал/канал/сейсмический объект.

## 2. Основной пользовательский сценарий

Пример для Мангистауской области / района Актау:

```text
Пользователь выбирает регион
        ↓
Мангистауская область
        ↓
Карта + список объектов
        ├── месторождения
        ├── проявления
        ├── структуры
        ├── скважины
        ├── сейсмические профили/площади
        ├── геологические карты
        └── внешние GIS-слои
        ↓
Выбор месторождения
        ↓
Полный паспорт месторождения
        ├── общая геология
        ├── положение и координаты
        ├── тектоника
        ├── стратиграфия
        ├── литология
        ├── залежи/горизонты
        ├── нефть / газ / вода
        ├── глубины и интервалы
        ├── скважины
        ├── сейсмика
        ├── ГИС/каротаж
        ├── керн и образцы
        ├── испытания пластов
        ├── давления/температуры
        ├── добыча — если данные доступны
        ├── документы
        ├── источники
        ├── конфликты данных
        └── история изменений
```

При выборе скважины пользователь получает вертикальный профиль/таймлайн по глубине:

```text
Скважина X
0 м
│
├─ траектория
│
├─ 950–1120 м  литология / стратиграфия
│
├─ 1180 м       каротажные кривые
│
├─ 1250–1280 м  вода
│
├─ 1430–1465 м  нефтепроявление
│
├─ 1510–1540 м  газ / испытание
│
└─ TD 1780 м
```

Это не схематичное заключение: пользователь должен иметь возможность открыть первичное доказательство для каждого интервала.

## 4. Что должно храниться о территории

### География

- административная область/район;
- координаты;
- границы;
- площадь;
- населённые пункты;
- дороги и инфраструктура — при наличии открытых данных;
- гидрография;
- рельеф/DEM;
- высота;
- land cover / спутниковые слои;
- охраняемые/ограниченные территории — если доступны легально.

### Региональная геология

- тектоническое положение;
- бассейн/провинция;
- структурно-тектонические элементы;
- стратиграфический разрез;
- геологический возраст;
- литология;
- разломы;
- соляная тектоника;
- нефтегазоносные комплексы;
- гидрогеология;
- полезные ископаемые;
- геологическая изученность.

## 5. Что должно храниться о месторождении

- официальное название RU/KK/EN;
- исторические и альтернативные названия;
- тип объекта;
- координаты/контур;
- административная принадлежность;
- бассейн/структура;
- статус изученности;
- дата/история открытия — если подтверждена источником;
- геологическое строение;
- тектоника;
- стратиграфия;
- продуктивные горизонты;
- литология коллекторов;
- тип коллектора;
- флюиды: нефть, газ, конденсат, вода;
- глубины кровли/подошвы и продуктивных интервалов;
- пористость;
- проницаемость;
- насыщенность — при наличии данных;
- давления;
- температуры;
- PVT/свойства флюидов — при наличии открытых данных;
- скважины;
- сейсмические исследования;
- геофизические исследования;
- испытания;
- источники и документы;
- конфликтующие значения;
- степень достоверности каждого утверждения.

## 6. Что должно храниться о скважине

### Паспорт

- название/номер;
- aliases;
- тип;
- статус;
- оператор/организация — если это публичные данные;
- дата заложения;
- дата окончания;
- проектная/фактическая глубина;
- устьевые координаты;
- исходная система координат;
- точность координат;
- высотная отметка;
- datum/reference elevation;
- назначение скважины.

### Траектория

Отдельные точки траектории:

- MD;
- TVD;
- TVDSS;
- inclination;
- azimuth;
- northing/easting или latitude/longitude;
- survey method;
- quality/provenance.

### Геологический разрез

Для интервалов:

- top/base MD;
- top/base TVD/TVDSS;
- стратиграфическая единица;
- локальный горизонт;
- литология;
- описание породы;
- возраст;
- коллекторские свойства;
- флюид;
- нефтегазопроявления;
- водопроявления;
- interpreted/evidence status.

## 7. ГИС / каротаж

ГИС в GeoKZ означает геофизические исследования скважин и не смешивается с Geographic Information System. В UI термин должен быть явно подписан: «ГИС скважины / Well logs».

Нужно поддержать:

- wireline logs;
- LWD/MWD;
- gamma ray;
- SP;
- resistivity;
- density;
- neutron;
- sonic/acoustic;
- caliper;
- temperature;
- pressure;
- image logs;
- cement evaluation;
- другие кривые через расширяемый справочник.

Модель:

```text
WellLogRun
    ├── well_id
    ├── run/type/service company
    ├── from/to depth
    ├── depth_reference
    ├── acquisition date
    ├── source/file
    └── curves[]

WellLogCurve
    ├── mnemonic_original
    ├── property_kind
    ├── unit_original
    ├── canonical_unit
    ├── index curve/depth
    └── samples/file reference
```

Кривые больших объёмов не следует хранить как миллионы строк ORM без необходимости. Метаданные и индексы находятся в PostgreSQL, а массивы/файлы могут храниться в специализированном файловом/object storage формате.

Для нормализации наименований кривых нужно ориентироваться на Energistics Practical Well Log Standard (PWLS).

## 8. Испытания скважин и пластов

Отдельная сущность `WellTest` должна представлять:

- тип испытания;
- интервал перфорации/тестирования;
- дата;
- пласт/горизонт;
- давление;
- температура;
- дебит;
- единица дебита;
- нефть;
- газ;
- вода;
- штуцер/режим — при наличии;
- продолжительность;
- результат;
- interpretation;
- source/evidence.

Типы могут включать DST, production test, injectivity, pressure transient и другие через controlled vocabulary.

## 9. Керн и образцы

```text
CoreRun
    ├── well
    ├── top/base depth
    ├── recovery
    └── samples

Sample
    ├── depth
    ├── sample type
    ├── lithology
    ├── porosity
    ├── permeability
    ├── density
    ├── saturation
    ├── laboratory measurements
    └── source
```

Параметры лабораторных анализов должны быть расширяемыми, с обязательной единицей измерения и методом анализа.

## 10. Сейсмика

GeoKZ должен хранить каталог сейсмических исследований и их пространственное положение.

```text
SeismicSurvey
    ├── 2D / 3D
    ├── name
    ├── acquisition dates
    ├── operator/contractor
    ├── coordinate reference system
    ├── coverage geometry
    ├── acquisition parameters
    ├── processing history
    └── datasets

SeismicLine (2D)
    ├── line name
    ├── geometry
    └── dataset reference

SeismicVolume (3D)
    ├── footprint
    ├── inline/crossline ranges
    ├── sample interval
    └── dataset reference
```

Сами большие SEG-Y файлы должны храниться вне основных таблиц PostgreSQL, а БД хранит каталог, checksum, storage URI, spatial coverage, технические metadata и provenance.

При импорте нужно учитывать SEG-Y rev 2.x; поддержка конкретных ревизий должна быть объявлена явно.

## 11. Интерпретации

Интерпретация должна храниться отдельно от наблюдения.

Например:

```text
Observation:
    газопроявление 1510–1540 м

Interpretation:
    продуктивный газонасыщенный горизонт
```

Они могут иметь разные источники и разный уровень доверия.

Возможные объекты интерпретации:

- seismic horizon;
- fault interpretation;
- formation top;
- fluid contact;
- reservoir interval;
- prospect;
- structural map.

## 12. Связь с доказательной моделью

Любое существенное значение может ссылаться на `Fact` / `FactEvidence`.

Пример:

```text
WellTest
  interval: 1510–1540 m
  gas_rate: 120000 m3/day
        │
        └── Evidence
              ├── report.pdf
              ├── page 73
              ├── table 5
              └── verified
```

Если другой источник сообщает другое значение, создаётся конфликт, а не бесследный overwrite.

## 13. Внешние интеграции

Источники должны подключаться через адаптеры. Категории:

### Kazakhstan

- data.egov.kz;
- открытые государственные геологические наборы;
- разрешённые публичные GIS/картографические сервисы;
- другие официальные API при наличии открытого доступа и понятной лицензии.

### International

- USGS;
- Macrostrat;
- OneGeology/OGC;
- Copernicus;
- другие открытые источники с совместимой лицензией.

### Industry file standards

- LAS/DLIS — well logs;
- WITSML 2.1 — бурение, траектории, well logs и связанные well data;
- SEG-Y — seismic;
- GeoJSON/GeoPackage — GIS;
- GeoSciML — геологическая модель/обмен;
- RESQML/PRODML — последующие этапы, если появится соответствующий открытый/корпоративный workflow.

## 15. Поиск

GeoKZ должен поддержать запросы уровня:

- «Мангистауская область»;
- «месторождения возле Актау»;
- «скважины глубже 3000 м»;
- «где обнаружен газ на глубине 1500–2000 м»;
- «скважины с нефтью, но без коммерческого притока»;
- «карбонатные коллекторы юры»;
- «все испытания горизонта X»;
- «какие сейсмические работы покрывают это месторождение»;
- «покажи источники, которые противоречат глубине кровли пласта».

Поиск объединяет relational filters, PostGIS, full-text search и позднее semantic search.

## 16. Приоритет достоверности

GeoKZ не утверждает, что один тип источника всегда истинен. Система хранит наблюдения и provenance, а предпочтительное значение определяется политикой качества и экспертной проверкой.

Проверенные данные GeoKZ являются master view, но внешние значения остаются доступными для сравнения.

## 17. Масштабирование

Не все данные должны физически храниться в PostgreSQL:

```text
PostgreSQL/PostGIS
    metadata, entities, intervals, relationships, search, geometry

Object/File Storage
    PDF/DOCX
    LAS/DLIS
    SEG-Y
    images
    large arrays
    exports
```

Это позволяет сохранять богатую предметную модель без превращения основной БД в файловое хранилище.

## 18. Отраслевые ориентиры

При проектировании необходимо учитывать:

- WITSML 2.1 для well/drilling/log data;
- Energistics PWLS для нормализации well log property kinds;
- SEG-Y rev 2.x для seismic exchange;
- GeoSciML для геологических объектов;
- OGC API Features / GeoPackage для GIS interoperability.

GeoKZ не обязан реализовывать эти стандарты полностью, но внутренняя модель не должна препятствовать их импорту/экспорту.
