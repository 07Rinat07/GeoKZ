# GeoKZ — трёхъязычная архитектура

GeoKZ является трёхъязычным приложением. Обязательные языки:

- `ru` — русский;
- `kk` — қазақ тілі;
- `en` — English.

## 1. Область локализации

Три языка поддерживаются для:

- пользовательского интерфейса;
- названий геологических объектов;
- административных регионов;
- справочников и controlled vocabularies;
- описаний, подготовленных внутри GeoKZ;
- API-представлений пользовательских текстов;
- поиска;
- пользовательских сообщений об ошибках;
- документации пользователя;
- экрана «О программе».

## 2. Исходные данные не подменяются переводом

Первичный материал всегда сохраняется без изменения:

- `original_text` факта;
- `quote_text` доказательства;
- OCR/raw text страницы;
- импортированный документ;
- RAW payload внешнего API.

Для исходного материала хранится язык оригинала. Если создаётся перевод, он является отдельным производным представлением и не заменяет исходник.

## 3. Технические идентификаторы не локализуются

Не переводятся UUID, `external_id`, API routes, enum codes, source codes, dataset codes и machine-readable статусы.

Например API стабильно возвращает:

```json
{"verification_status": "VERIFIED"}
```

а UI отображает:

```text
ru: Проверено
kk: Тексерілген
en: Verified
```

## 4. Предметные названия

Для основных канонических названий допустима и уже используется модель:

```text
name_ru
name_kk
name_en
```

Для нескольких вариантов названия используется `entity_names`:

```text
entity_id
name
language
name_type
source_id
is_preferred
```

Канонический мастер-контент GeoKZ ограничивается `ru`, `kk`, `en`. Исходные документы и внешние записи могут иметь другой язык; их оригинальный язык хранится отдельно.

## 5. Fallback

Рекомендуемый порядок fallback зависит от выбранного языка интерфейса:

- `ru`: `ru → kk → en`;
- `kk`: `kk → ru → en`;
- `en`: `en → ru → kk`.

Fallback должен быть видимым на уровне presentation/service и не должен копировать текст между языковыми полями в БД.

## 6. API locale

API должен принимать язык через `Accept-Language` и, где это удобно для клиента, через параметр `lang=ru|kk|en`. Machine-readable поля остаются неизменными.

Для объектов API может отдавать как все локализации, так и вычисляемое display-поле:

```json
{
  "name_ru": "Прикаспийская впадина",
  "name_kk": "Каспий маңы ойпаты",
  "name_en": "Caspian Depression",
  "display_name": "Каспий маңы ойпаты"
}
```

## 7. Поиск

Поиск должен индексировать:

- `name_ru`;
- `name_kk`;
- `name_en`;
- синонимы;
- исторические названия;
- транслитерации;
- OCR-варианты.

Для русского и казахского текста должны учитываться Unicode-нормализация и регистр. Транслитерация рассматривается как дополнительный alias, а не как замена оригинального названия.

## 8. UI

PySide6-клиент хранит интерфейсные строки в ресурсах локализации и позволяет переключить язык без изменения предметных данных. Выбранный язык пользователя хранится как пользовательская настройка.

Первая версия UI обязана иметь полный набор строк для `ru`, `kk`, `en`; отсутствие перевода считается дефектом локализации.
